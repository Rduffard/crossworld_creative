# Watchtower verification and release

Run `npm run verify:operations -- frontend` in the frontend checkout for Operations lint and the production build. Use `backend` for the backend fast suite, Operations integration tests, the shared HTTP contract, and isolated supervisor tests. Use `release` for both. The backend defaults to the sibling checkout. `WATCHTOWER_BACKEND_PATH` can point to another candidate checkout.

The command stores a JSON receipt in the OS temporary directory under `crossworld-verification`. Set `WATCHTOWER_EVIDENCE_DIR` to select another directory outside the repositories. The receipt includes repository commit, content digest, timing, scope, and each check's exit status. A changed source tree invalidates the run. A dirty checkout can pass development checks but cannot produce a receipt marked as matching a committed candidate. Run release checks from a clean checkout of the actual commit, and compare its commit and content identity with the receipt. The receipt does not carry raw command output or replace GitHub's independent build.

Batch compatible frontend changes in one release. GitHub continues to install dependencies, build the candidate, and deploy the resulting files. Documentation-only pushes skip the frontend deploy. An active frontend deploy runs to completion.

The current backend release script swaps files while its PM2 API process is stopped. Media transfer exchange also lives in process memory. A running lease check alone has a race with the next relay claim. Keep verified backend work local until the owner has authorized a maintenance window, dispatch is held, active and in-flight claims and media transfers have drained, and the legacy relay can remain connected throughout the change. Automated deferred activation needs a server-side admission gate and durable release state that survive the API restart. An idle observation alone does not establish that condition.

The Artifacts workspace uses the authenticated Operations media endpoint. Ready images and supported videos remain on the registered storage device, and metadata remains available when a device is offline. Candidate review requires the new backend. An approval records a review decision and does not publish or promote artwork. Squash remains the authoritative home for defects. The Quality workspace uses its authenticated project and defect collections, with defect detail links going to standalone Squash.
